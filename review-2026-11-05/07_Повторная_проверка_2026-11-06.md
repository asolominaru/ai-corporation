## Подтверждённые проблемы текущей версии

### R-01. API принимает подставленную личность владельца и проверяющего — критично до подключения реальных действий

`services/orchestrator/app/main.py`: `_require_owner` сравнивает строку из JSON с allowlist. `/review` также доверяет `reviewer_id`, а `/complete` принимает `ci_passed` и произвольный непустой `ci_evidence`. Аутентифицированного контекста запроса нет.

**Воспроизведение:** запросы без заголовков аутентификации с тестовым `decided_by=owner-1`, ID назначенного проверяющего и выдуманной строкой CI довели задачу с обязательным human approval до `completed` (HTTP 200). Чужое имя отклоняется, но знание разрешённого имени достаточно. ID владельца не должен служить паролем.

**Исправить:** аутентифицировать сервисы/пользователя; tenant, actor и права определять на сервере; ограничить прямую запись решений; получать CI-результат из доверенного источника с привязкой к версии результата. Telegram-бот должен передавать проверенное решение через защищённый интерфейс. Тест без credentials обязан возвращать 401/403, даже если JSON содержит правильное имя владельца.

### R-02. Согласование может не относиться к текущему результату — высокая важность

`main.py`: `/complete` разрешает approval без сравнения версий, если у задачи отсутствует `artifact_sha256`. `/report` обновляет hash лишь при непустом значении и сохраняет старый hash при следующем отчёте без него.

**Воспроизведены два сценария:** (1) отчёт и approval без hash → `completed`; (2) approval версии A, request_changes, новый отчёт без hash → старое approval снова позволяет `completed`. Сам файл сервер также не проверяет: hash поступает от клиента.

**Исправить:** обязательная неизменяемая версия результата, hash вычисляется по сохранённому артефакту; новая попытка сбрасывает прежние review/approval; завершение проверяет цепочку «версия → проверка → CI → решение». Отсутствие hash — отказ для действий, требующих согласования версии.

### R-03. Новый model-router позволяет направить ключ провайдера на клиентский адрес — критично до подключения ключей

`services/model-router/app/main.py`: регистрация `/models` доступна без аутентификации и принимает `endpoint_config.base_url`. `app/providers.py` использует этот адрес вместе с серверным ключом выбранного провайдера в Authorization.

**Безопасное воспроизведение:** зарегистрирована тестовая модель с адресом `https://untrusted.invalid/v1`; HTTP-клиент заменён заглушкой; единственный ключ — искусственная строка. Заглушка получила запрос на заданный адрес с этим ключом. Внешних запросов и передачи настоящего секрета не было. Это доказательство пути утечки при доступности API и подключении рабочего ключа, не утверждение о произошедшей утечке.

**Исправить:** закрыть управление реестром административной ролью; адреса провайдеров выбирать из серверного allowlist; произвольные endpoint не должны получать ключи; убрать прямой доступ браузера к шлюзу моделей. Отдельный тест должен доказывать, что неразрешённый URL отвергается до HTTP-запроса.

### R-04. Бюджет нового router ещё не гарантирует заданный предел — высокая важность

Подтверждены отдельными тестами:

1. `/complete` принимает выдуманные tenant/task и установленный клиентом бюджет; реестр задач orchestrator не запрашивается.
2. Два перекрывающихся вызова одной задачи оба проходят предварительную проверку. При лимите $0.00031 и двух фактических расходах по $0.0002 итог $0.0004. Перекрытие смоделировано вложенным вторым запросом в момент ожидания ответа провайдера первого. Day/month резерв есть, общего атомарного резерва задачи нет.
3. При моделируемом переходе 30 ноября → 1 декабря резерв остаётся в старых day/month строках, фактический расход не попадает ни в одну строку, а reservation получает `committed`: settlement использует текущий период, а не период резерва.
4. Смоделированный ответ провайдера с расходом выше оценки принимается и превышает task/day cap. Этот тест показывает отсутствие контроля расхождения оценки и факта; размер токенов синтетический, не результат реального вызова.

**Исправить:** бюджет/tenant/privacy брать из авторитетной задачи; резервировать task/day/month вместе; хранить идентификаторы периодов в резерве; сделать settlement идемпотентным; оценивать вход на сервере и обеспечивать консервативный предел до платного запроса. Уже понесённый расход нужно честно записывать, а не скрывать отказом после вызова; перерасход блокирует следующие вызовы и требует разбора. Добавить конкурентные, календарные и recovery-тесты. В текущем дереве router штатных тестов не найдено.

Для эксплуатации нужен транзакционный реестр или блокировка процесса. Печать ошибки с exit 0 также мешает контролировать постоянную неисправность.

## Новый порядок работ для KIMI

1. **Закрыть R-01 и R-03 до подключения рабочих ключей и реальных действий.** Критерий: неавторизованный клиент не читает/меняет чужие задачи, не принимает решения и не меняет адреса моделей.
2. **Закрыть R-02 и R-04.** Критерий: новая версия требует новой проверки; повторные/конкурентные запросы и переход суток/месяца не обходят бюджет; стоимость и tenant берутся из доверенных источников.
3. **Соединить существующие компоненты в один серверный процесс обработки задачи.** Browser вызывает orchestrator; router — единственный путь к моделям; Telegram сообщает решение по точной версии; UI показывает ошибку/блокировку и восстанавливает задачу после перезапуска. Прямой обход model-router запрещён.
4. **Показать один полный пилот редакции «Сила малых групп».** Тема → источники → черновик → независимая содержательная проверка → замечания/доработка → конкретная версия для владельца → сохранённый принятый материал. Публикация отдельным действием по явному решению владельца. Для первой демонстрации — тестовые данные и бесплатные заглушки, затем ограниченный платный пилот в согласованном бюджете.
5. **Принимать результат по бизнес-пользе.** В карточке видны результат, ссылка на источники, стоимость попыток, активное время человека, причина ожидания и следующее действие. Технический uptime и разница между timestamp не заменяют человеческое время. Проверить сценарии «провайдер упал», «владелец отклонил», «материал изменён», «бюджет исчерпан», «приложение перезапущено».

Не расширять количество отделов и инфраструктуры до успешного пилота. Согласовать расхождение шести направлений в owner-config и пяти в blueprint, сохранив исходное решение владельца.
