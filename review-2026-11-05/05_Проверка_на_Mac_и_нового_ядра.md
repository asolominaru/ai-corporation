## Проверки нового кода

Штатные тесты: **17 passed, 1 warning**.

Тесты выполнялись в отдельной временной копии, с существующим Python-окружением сервиса и SQLite в памяти. Рабочий dev.db не использовался. FastAPI TestClient исполняет настоящий код приложения без открытого сетевого порта.

Дополнительные проверки: **6 сценариев воспроизведения подтвердили дефекты**. В этом наборе PASS означает «ошибка воспроизведена», а не «защита работает». Исходник — check_new_orchestrator.py; машинный итог — 06_Проверка_нового_orchestrator.json.

### N-01 — HIGH перед реальным использованием: можно завершить задачу без доказательств

[app/main.py:284](</Users/solominaag/КОРПОРАЦИЯ/KIMI  КОРПОРАЦИЯ/КОРПОРАЦИЯ/founder-ai-os/services/orchestrator/app/main.py:284>), [app/statemachine.py:104](</Users/solominaag/КОРПОРАЦИЯ/KIMI  КОРПОРАЦИЯ/КОРПОРАЦИЯ/founder-ai-os/services/orchestrator/app/statemachine.py:104>).

Создана задача с requires_human_approval=["high_risk_deploy"]. Через /transition последовательно переданы queued, running, review, approved, completed от того же исполнителя, с ci_passed=true. Каждый запрос получил HTTP 200. Не создавались claim/run, report, решение назначенного reviewer, запись owner approval или доказательство выполнения CI.

Сервис проверяет допустимость названий и последовательности статусов, но не проверяет факты, дающие право на переход. «Побывала в статусе review» не равно «прошла независимое ревью».

Исправление: убрать произвольные переходы для клиентов; отдельные команды submit/review/approve/complete с серверной проверкой actor, назначений, артефакта, отчёта, CI evidence и обязательных человеческих решений. Требуемые approval должны проверяться непосредственно перед защищённым действием.

[app/main.py:105](</Users/solominaag/КОРПОРАЦИЯ/KIMI  КОРПОРАЦИЯ/КОРПОРАЦИЯ/founder-ai-os/services/orchestrator/app/main.py:105>), [app/main.py:186](</Users/solominaag/КОРПОРАЦИЯ/KIMI  КОРПОРАЦИЯ/КОРПОРАЦИЯ/founder-ai-os/services/orchestrator/app/main.py:186>).

Создан tenant B. API принял его задачу с project_id tenant A, а затем разрешил агенту A забрать задачу B. Проверяется существование сущностей, но не совпадение их tenant_id.

Исправление: tenant из аутентифицированного контекста, проверки принадлежности всех связанных объектов, ограниченные роли БД и RLS. Тестировать и чтение, и запись, и claim.

### N-03 — HIGH для контроля расходов: бюджет сравнивается с одной попыткой

[app/main.py:219](</Users/solominaag/КОРПОРАЦИЯ/KIMI  КОРПОРАЦИЯ/КОРПОРАЦИЯ/founder-ai-os/services/orchestrator/app/main.py:219>), [app/main.py:257](</Users/solominaag/КОРПОРАЦИЯ/KIMI  КОРПОРАЦИЯ/КОРПОРАЦИЯ/founder-ai-os/services/orchestrator/app/main.py:257>).

При бюджете $0.50 две попытки по $0.40 обе закончились review без блокировки, хотя сумма $0.80. Отдельно API принял cost_usd=-100 и tokens_in=-10.

Это не работающий финансовый стоп-лимит: код принимает заявленную агентом стоимость уже после работы; он не резервирует деньги перед вызовом модели и не учитывает накопленные затраты.

Исправление: неотрицательные конечные числа; доверенный учёт на gateway; сумма всех попыток/моделей/review; резерв до вызова; независимые task/day/month лимиты и атомарные проверки.

### N-04 — HIGH для согласований: личность задаёт сам вызывающий, expiry игнорируется

[app/main.py:320](</Users/solominaag/КОРПОРАЦИЯ/KIMI  КОРПОРАЦИЯ/КОРПОРАЦИЯ/founder-ai-os/services/orchestrator/app/main.py:320>), [app/main.py:341](</Users/solominaag/КОРПОРАЦИЯ/KIMI  КОРПОРАЦИЯ/КОРПОРАЦИЯ/founder-ai-os/services/orchestrator/app/main.py:341>).

В тесте approval имел expires_at в прошлом. Запрос с decided_by="unverified-caller" принят и изменил его на approved.

README честно сообщает об отсутствии аутентификации в P0. Это допустимое ограничение лабораторного прототипа, но не доказанная защита владельца. Tailscale или localhost сами по себе не определяют, кто имеет право согласовать конкретное действие.

Исправление: аутентифицированный actor, проверка полномочий/tenant, срока, версии артефакта и ожидаемого действия; транзакционный conditional update pending → decided. Нынешний последовательный тест повторного решения проходит; защиту от двух одновременных решений он не доказывает.

### N-05 — MEDIUM/HIGH для достоверности журнала: hash-chain не защищает автора и действие

[app/audit.py:43](</Users/solominaag/КОРПОРАЦИЯ/KIMI  КОРПОРАЦИЯ/КОРПОРАЦИЯ/founder-ai-os/services/orchestrator/app/audit.py:43>), [app/audit.py:60](</Users/solominaag/КОРПОРАЦИЯ/KIMI  КОРПОРАЦИЯ/КОРПОРАЦИЯ/founder-ai-os/services/orchestrator/app/audit.py:60>).

В изолированной БД после записи аудита изменены actor_id и action. /audit/verify продолжил возвращать chain_valid=true: hash охватывает payload и предыдущий hash, но не автора, действие и остальные существенные поля.

Это не доказательство внешнего взлома. Это конкретная граница алгоритма проверки, противоречащая сильной формулировке «неизменяемый аудит».

Исправление: канонический hash полного события, права append-only, стабильная последовательность и сериализация конкурентных записей, внешний контрольный hash/экспорт. Подмены полей события должны обнаруживаться тестом.

## Что в новом сервисе полезно

- Появился настоящий FastAPI API и ORM-модели.
- Есть валидация Task Protocol, запрет части недопустимых переходов и тесты.
- Есть единое место для разработки будущих checks и журналирования.
- В README явно указаны ограничения dev-версии, отсутствие auth, Telegram-интеграции и миграций.

Эту работу стоит сохранить и исправить. Она меняет статус проекта с «документы плюс отдельные прототипы» на «документы, интерфейс и начатое серверное ядро».

## Что пока не связано

- Новый backend не связан с визуальной панелью и существующим Telegram-ботом; main.py:337 содержит TODO отправки в Telegram.
- Model router в этом сервисе не реализован.
- PostgreSQL/RLS/Alembic описаны как последующая работа. create_all выполняется без условия при старте; Postgres-ready эксплуатация не доказана.
- Claim не содержит реализации FOR UPDATE SKIP LOCKED.
- Docker-сборка сервиса и интеграция с общим Compose не появились в просмотренном комплекте.
- /health возвращает статическое ok; он сам по себе не подтверждает доступность БД, очереди, моделей и всей системы.

## Что делать дальше

Сначала закрыть N-01, N-02, N-03 и N-04 на уровне backend и превратить воспроизведения в тесты, ожидающие отказа. Затем связать один редакционный процесс с постоянными артефактами и безопасным owner approval. После этого расширять router и панель.

Запрашивать повторно приоритет «редакция первой» на основании старого отчёта не нужно: он уже явно задан в ChatGPT-чате; в Kimi дополнительно существует запись согласования порядка MVP. Числовой предел $15/день при этом не равен полной месячной смете ~$280: при ежедневном достижении потолка только API составит $450 за 30 дней, плюс инфраструктура. Это арифметика лимита, не оценка фактических расходов.

Исходный код, cron, рабочая БД, аккаунты и серверы при проверке не изменялись. Боту и Kimi новые сообщения не отправлялись. Проверена реализация на Mac и доступный интерфейс Kimi; чужие серверы не обследовались.
